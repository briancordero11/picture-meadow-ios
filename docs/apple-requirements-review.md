## App Privacy: offline and optional service differ

Apple excludes purely on-device processing from its collection definition. Off-device information counts when readable access lasts beyond servicing the real-time request. Stored IP addresses must be classified according to their use. Optional functionality does not automatically qualify for optional disclosure. [App Privacy Details, “Data collection,” “Optional disclosure,” and “Additional guidance”](https://developer.apple.com/app-store/app-privacy-details/)

**Implementation assessment:** the offline configuration has no app-operated network service enabled, with both an empty API URL and an explicit disabled feature flag. Optional descriptions send category, destination, coaster color, and animal IDs; they do not send the board phrase. The server does not persist request bodies, but its rate limiter holds socket addresses/counts in memory and now removes expired entries on a scheduled sweep, even while idle. Default retention is normally 60–61 seconds, subject to event-loop delay. Proxy/hosting logs are independent. Do not finalize a “Data Not Collected” answer for online deployment without auditing retention and disclosures. This is an inference from the source rule and repository behavior, not Apple's classification of this app.

Keep the optional service disabled until its operator, endpoint, vendor access, retention, and disclosure choices are known. Document local retention accurately: turning remembering off removes the persisted wish; reset clears the current wish/phrase; local speech generation is not audio recording. Device/system backup behavior should be explained where relevant, without promising that uninstall/reset erases independent backups or provider logs.

Native code now uses a temporary session without shared cookies, credentials, or a cache, rejects cross-origin/non-HTTPS redirects, and cancels adult authorization/requests on session exit or inactivity. A native notice explains local storage, clearing choices, online request contents, and connection metadata. These are inspected code changes; their compilation and runtime behavior remain unverified on Windows. See `backend-privacy-review.md` for the service audit, and `privacy-policy-draft.html` for the explicitly incomplete policy draft.

Release metadata must reflect the confirmed `US` launch, separate independent LLC, and declared **"2 - 17+"** audience without inventing the LLC's legal name, contact details, or public URLs. The machine-readable record uses `statedAgeRange: "2–17+"`, `minimumAge: 2`, and `maximumAge: null`; null explicitly means **open-ended**, not an omitted decision or an inferred age cap. Kids Category remains undecided. `scripts/check-release-metadata.py` checks the completed release record, not App Store Connect availability, the account, or the compiled app, and does not certify approval.

For the confirmed U.S. audience, under-13 users are intentionally included. FTC guidance covers commercial child-directed apps that collect personal information; that can include qualifying persistent identifiers, not just names or photos. Any internal-operations exception is conditional, not presumed from having no accounts. Review the actual online data flow before enabling it; this note does not establish COPPA compliance or call for new age/identity collection. [FTC: Six-Step COPPA Compliance Plan, Step 1](https://www.ftc.gov/business-guidance/resources/childrens-online-privacy-protection-rule-six-step-compliance-plan-your-business), [FTC COPPA FAQs, coverage and persistent-identifier/internal-operations questions](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions). The app's adult gate remains distinct from verifiable parental consent.

Developers remain responsible for required age checks and significant-update restrictions. Apple's current Q&A describes 26.2 SDK/Xcode 26.2 for the expanded framework set, 26.4 regulatory/significant-update APIs, and the 26.5 `confirmed` result replacing specific card/ID confirmation results.
